# ADR 0007 — Editable asset document contract

Status: accepted  
Date: 27 August 2026  
Supersedes: nothing  
Relates to: AST-600, AST-601, AST-602, AST-603

## Context

The Asset Studio grew from one pixel-asset document to six document types:
pixel assets, tile maps, palettes, character sets, screens and songs. Without a
stated contract each new type risked inventing its own validation, its own idea
of what "generated" means, and its own answer to what happens when a document
does not fit the machine it targets. This decision records the contract every
editable asset document in this repository follows, so a seventh type has a rule
to follow rather than a precedent to guess at.

## Decision

### Schema and versioning

Every document is a JSON object with a `schema` string and an integer `version`.
The schema names are `8bit-net.pixel-asset`, `8bit-net.tile-map`,
`8bit-net.palette`, `8bit-net.font`, `8bit-net.screen` and `8bit-net.song`. A
parser rejects any document whose schema or version it does not know, by name,
rather than attempting a best-effort read.

Every type exposes exactly three functions with the same shape:

- `parseXDocument(value)` accepts a JSON string or an object, validates it
  completely, and returns a normalized document or throws an `Error` whose
  message names the specific field that was wrong.
- `serializeXDocument(document)` validates and returns pretty-printed JSON with
  a trailing newline.
- `generateXOutput(document)` returns `{ bytes, assembly, manifest }` and, where
  a BASIC form is meaningful, `basic`.

Parsing is total: it either produces a document that satisfies every declared
constraint, or it throws. It never returns a partially repaired document.

### Migration policy

New fields are added with a documented default so that an older document still
parses; that is how tile-map tile properties and the song hardware target were
added without a version bump. A change that would make an existing document
parse differently, rather than merely gain a default, requires a new `version`
and an explicit migration in the parser, following the precedent already set by
the pixel-asset legacy-draft migration and by project format versions 1 to 17.
Unknown fields are not silently dropped where the document type declares an
`extensions` object; that object is preserved verbatim so third-party data and
import provenance survive a round trip.

### Target capability declaration

A document may not describe hardware the target does not have. Each type
declares its own capabilities and refuses anything beyond them at the parser, not
merely in the interface:

- palettes declare the logical-colour count of each display mode and require
  exactly that many entries;
- screens derive resolution, colour depth and frame-buffer size from the mode
  and reject a frame buffer of any other length;
- songs declare channels, maximum volume and row limits per sound target, so an
  Atom song cannot be given four channels or a volume above one;
- tile maps refuse a cell that names an index the tileset does not declare.

### Generated output and manifests

Generation is a pure function of the document: the same document always produces
the same bytes. Every generator returns a manifest carrying the source schema
and version, the identity of what was generated, its byte length and a SHA-256
digest of the generated bytes. Where generation cannot fully satisfy a request
the manifest says so in data rather than in prose: a tile index with no artwork
chosen, the logical colours a screen actually uses, the rows of a song that are
silent, the character codes defined outside the machine's reserved range.

### Build integration

Each type has an `INCLUDE…` directive in the browser-local 6502 assembler:
`INCLUDEASSET`, `INCLUDEMAP`, `INCLUDEPALETTE`, `INCLUDEFONT`, `INCLUDESCREEN`
and `INCLUDESONG`. A directive emits the generated source at the current address,
reports a missing or malformed document as a build diagnostic located at the
requesting line, and registers the document as a real build input in both the
incremental dependency graph and the content-addressed cache, so editing a
document stales the artifact. Transitive inputs count: a map's tileset artwork
is an input of any build that includes the map.

### Editing and performance

Documents are immutable values; an editing helper returns a new document and
re-validates. Where a document's payload is large, an editor holds the decoded
payload as its working state and constructs a document only when one is needed,
because validating and re-encoding a whole payload per keystroke is not an
interactive cost. That is why the screen editor keeps a `Uint8Array` frame
buffer and debounces persistence: measured on MODE 0, painting through the
decoded buffer is 0.025 ms per pixel against 6.9 ms through the document API.

### Accessibility

Every editor that draws to a canvas also exposes its state as text: the cell or
pixel under a keyboard cursor, and for the tile map the indices of the current
row. An editor must remain operable and readable when no 2D context is
available.

## Consequences

- A new asset type has a checklist rather than a precedent to interpret.
- Property and fuzz coverage can be written once against the shared shape; it is,
  in `src/assets/assetCodecProperties.test.ts`, which exercises every codec for
  round-trip stability, mutation tolerance and refusal of hostile input.
- The contract forbids the shortcut of accepting a document the target machine
  cannot honour and correcting it later, which is what keeps generated output
  from claiming hardware behaviour the machine does not have.
